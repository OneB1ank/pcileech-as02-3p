# Vivado programming

This guide covers JTAG chain detection, volatile FPGA programming, generation
of a persistent SPIx4 image, indirect programming of the board's configuration
Flash, and the handoff to PCIe/SFP1 bring-up.

The confirmed configuration memory is one **Micron MT25QU256**, a **256 Mbit
(32 MiB), single-device QSPI x4** Flash.

## Current bench status

As observed on **September 17, 2026**, Vivado Hardware Manager detects the
programmer/target but does not list `xcku3p_0`. This means the JTAG device gate
is still open:

- no FPGA is currently available to **Program Device**;
- the MT25QU256 also cannot be programmed indirectly through the FPGA;
- this state is a board power/JTAG/VREF/chain issue, not evidence that any BIT
  or MCS image is defective.

Continue with image programming only after `xcku3p_0` appears in
`get_hw_devices` or the Hardware Manager device tree.

This current state is separate from an **August 26, 2026 historical external
baseline diagnostic**. In that earlier session, `xcku3p_0` was visible, Vivado
selected `mt25qu256-spi-x1_x2_x4`, and Erase plus Program/Verify completed for
the external Corundum image. A subsequent JTAG refresh reported `DONE_PIN=1`
and `ISC_DONE=1` after `boot_hw_device`.

That historical MCS was generated with `write_cfgmem -size 256`. Vivado 2024.2
interprets that value as **256 MBytes**, and its PRM records address range
`0x00000000..0x0FFFFFFF`. It is therefore an old connectivity/Flash-path
diagnostic, not the correct 32 MiB MT25QU256 mapping, not a project release
image, and not evidence of a full physical power-cycle boot.

## Choose an image

The normal release build uses `AS02_PROJECT_DIR=.build/release` and produces:

- `as02_asmcehnk_25g/.build/release/fpga.xpr`;
- `as02_asmcehnk_25g/.build/release/fpga.runs/impl_1/fpga.bit`;
- `as02_asmcehnk_25g/.build/release/fpga.runs/impl_1/fpga.bin`.

Use the normal `fpga.bit` for functional bring-up and as the source for the
persistent MCS. A normal build only emits `fpga.ltx` when the design contains
debug cores.

The hardware-debug build is started from `as02_asmcehnk_25g/` with:

```powershell
vivado -mode batch -source .\vivado_build_debug_as02.tcl -notrace
```

It produces `fpga_debug.bit`, `fpga_debug.bin`, and `fpga_debug.ltx` in that
directory. Always load `fpga_debug.bit` with the `fpga_debug.ltx` generated by
the same build. The debug image is intended primarily for temporary JTAG/ILA
work; use a validated normal image as the default persistent Flash image.

## Recover and verify the JTAG chain

1. Install the Vivado 2024.2 Kintex UltraScale+ device files.
2. Power the board from its supported source. A PCIe slot may provide the board
   power used during endpoint testing; JTAG recognition still requires stable
   board power.
3. Connect TCK, TMS, TDI, TDO, GND, and VREF according to the board schematic
   and programmer documentation. VREF is the programmer's I/O voltage
   reference, not an assumed board-power output.
4. In Vivado select **Open Hardware Manager → Open Target → Auto Connect**.
5. Confirm that `xcku3p_0` appears below the hardware target.

If Vivado reports **No devices detected** or shows only the programmer:

- confirm board power and common ground;
- measure/confirm the expected VREF at the programmer;
- recheck TDI/TDO direction and the complete pin order;
- reconnect the target after a board/programmer power cycle;
- reduce the JTAG clock if the cable supports that setting;
- restart `hw_server`/Hardware Manager and repeat **Auto Connect**.

Do not proceed to **Add Configuration Memory Device** until the FPGA is present.
The Flash is reached indirectly through a configured JTAG-visible FPGA; it is
not expected to appear as an independent JTAG device.

Seeing `xcku3p_0` proves only that the FPGA is visible on JTAG. It does not prove
successful configuration, PCIe enumeration, Flash boot, SFP1 link, BAR/DMA, or
LeechCore operation.

## Temporarily program the FPGA

Use volatile programming before writing Flash:

1. In Hardware Manager, select `xcku3p_0` and choose **Program Device**.
2. Set **Bitstream file** to the selected `.bit` file.
3. For a debug image, set **Debug probes file** to the matching `.ltx`; leave it
   empty for a normal image that has no probes file.
4. Select **Program** and wait for Vivado to report success.
5. Refresh the device. For a debug image, confirm the expected ILA cores appear.

Recommended diagnostic order after the chain is restored:

1. Temporarily load the external known-good board baseline and record the
   result.
2. Temporarily load this project's normal `fpga.bit` and record the result.
3. Continue to Flash only after the intended normal image works in volatile
   mode.

The `.bit` file configures FPGA SRAM. It is lost after power-off or another
configuration event.

## Generate the SPIx4 MCS

The normal and debug builds call `write_bitstream -bin_file`, so they emit
`.bit` and `.bin`. They do not currently call `write_cfgmem`; generate the MCS
as a separate release step from the validated normal BIT.

The active XDC already specifies:

- `CONFIG_MODE SPIx4`;
- `BITSTREAM.CONFIG.SPI_BUSWIDTH 4`;
- `CONFIG_VOLTAGE 1.8`;
- `BITSTREAM.CONFIG.CONFIGRATE 72.9`;
- `BITSTREAM.CONFIG.SPI_FALL_EDGE Yes`.

In the Vivado Tcl Console, use forward-slash paths and generate a 32 MiB
(256 Mbit), SPIx4 image loaded at address zero:

```tcl
write_cfgmem -force -format mcs -interface SPIx4 -size 32 \
    -loadbit "up 0x00000000 C:/path/to/fpga.bit" \
    -checksum -file C:/path/to/fpga.mcs
```

Vivado 2024.2 defines `write_cfgmem -size` in **MBytes**. MT25QU256 is
256 Mbit = 32 MiB, so the correct value is `-size 32`. The command shape,
capacity, and address range were validated offline using the external diagnostic
BIT as input: Vivado reported `Size 32M`, address range
`0x00000000..0x01FFFFFF`, and generated both MCS and PRM with zero warnings or
errors. This validates the cfgmem-generation recipe only; generation, Flash
programming, and boot of an MCS made from this project's normal `fpga.bit`
remain open hardware/release gates.
Keep the generated `.mcs` and `.prm` together with the source BIT and their
hashes. The MCS load address for the single boot image is `0x00000000`.

## Attach and program the MT25QU256

Vivado 2024.2 on the build workstation was queried with:

```tcl
get_cfgmem_parts *mt25qu256*
```

The catalog contains both expected single-device choices. In Hardware Manager:

1. Right-click `xcku3p_0` and choose **Add Configuration Memory Device**.
2. Search for `mt25qu256`.
3. Prefer `mt25qu256-spi-x1_x2_x4`.
4. If the board/catalog workflow requires the explicit topology entry, select
   `mt25qu256-qspi-x4-single`.
5. Confirm the selected topology is one device and x4-capable.

Do not select:

- `dual_stacked`;
- `dual_parallel` or x8 dual-parallel;
- BPI entries;
- a different capacity.

Vivado may ask whether to program the configuration memory after attaching it.
Choose the generated `fpga.mcs`, then enable:

- **Erase**;
- **Program**;
- **Verify**.

Run **Program Configuration Memory Device** and retain the log showing the
result of all three operations. A Verify PASS proves the programmed contents can
be read back; it does not yet prove the board boots from Flash.

## Verify power-cycle boot and PCIe enumeration

Persistent configuration has its own acceptance gate:

1. Complete Erase/Program/Verify without errors.
2. Remove board power so the volatile SRAM configuration is lost.
3. Reapply power with the board boot mode set for Master SPI/QSPI.
4. Reconnect Hardware Manager and confirm the FPGA configured from Flash.
5. Cold-boot or reset the PCIe host so the configured endpoint is present during
   Root Complex enumeration.
6. Confirm endpoint identity, negotiated width/rate, BAR0, and capabilities.

Refreshing Device Manager alone does not guarantee PCIe link retraining or a
complete Root Complex enumeration. For acceptance, use a power/reset sequence
that makes the endpoint available before enumeration.

After PCIe enumeration, continue with [Board bring-up](board-bringup.md). The
RawUDP cable and packet tests use physical **SFP1 / RTL lane 0** only. **SFP2 /
lane 1** remains TX-idle and RX-drain.

## Record programming evidence

Record the source commit and image hashes before board testing:

```powershell
git rev-parse HEAD
Get-FileHash -Algorithm SHA256 .\.build\release\fpga.runs\impl_1\fpga.bit
Get-FileHash -Algorithm SHA256 .\fpga.mcs, .\fpga.prm
Get-FileHash -Algorithm SHA256 .\fpga_debug.bit, .\fpga_debug.ltx
```

For volatile programming, retain the BIT/LTX pair when applicable and the
Vivado Program Device log. For persistent programming, retain the source BIT,
MCS/PRM, selected cfgmem part, Erase/Program/Verify log, power-cycle result, and
PCIe enumeration output. See [Validation status](validation.md) for the
distinction between JTAG visibility, volatile configuration, Flash verification,
power-cycle boot, and complete hardware acceptance.
