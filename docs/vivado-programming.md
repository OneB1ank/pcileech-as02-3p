# Vivado programming

This guide covers volatile JTAG programming and the handoff from Vivado to the
hardware bring-up procedure. It does not define a persistent QSPI image because
the exact configuration-memory device has not yet been confirmed in this
repository.

## Choose an image

The normal release build uses `AS02_PROJECT_DIR=.build/release` and produces:

- `as02_asmcehnk_25g/.build/release/fpga.xpr`
- `as02_asmcehnk_25g/.build/release/fpga.runs/impl_1/fpga.bit`
- `as02_asmcehnk_25g/.build/release/fpga.runs/impl_1/fpga.bin`

Use `fpga.bit` for normal JTAG programming. A normal build only emits
`fpga.ltx` when the design contains debug cores.

The hardware-debug build is started from `as02_asmcehnk_25g/` with:

```powershell
vivado -mode batch -source .\vivado_build_debug_as02.tcl -notrace
```

It produces `fpga_debug.bit`, `fpga_debug.bin`, and `fpga_debug.ltx` in that
directory. Always load `fpga_debug.bit` with the `fpga_debug.ltx` generated by
the same build. A mismatched probes file makes ILA/VIO signals unreliable.

## Connect the hardware

1. Install the Vivado 2024.2 Kintex UltraScale+ device files.
2. Power the board from its supported source. A PCIe slot may provide the board
   power used during endpoint testing; JTAG recognition still requires the
   board to be powered.
3. Connect the programmer's TCK, TMS, TDI, TDO, GND, and VREF according to the
   board schematic and programmer documentation. Treat VREF as the programmer's
   I/O voltage reference, not as an assumed board power output.
4. Start Vivado, open **Hardware Manager**, select **Open Target**, then
   **Auto Connect**.
5. Confirm that the JTAG chain contains `xcku3p_0`.

Seeing `xcku3p_0` proves only that the FPGA is visible on JTAG. It does not prove
PCIe enumeration, SFP1 link, UDP operation, BAR/DMA behavior, or LeechCore
operation.

## Program through Hardware Manager

1. In Hardware Manager, select `xcku3p_0` and choose **Program Device**.
2. Set **Bitstream file** to the normal `fpga.bit` or the debug
   `fpga_debug.bit` selected above.
3. For the debug image, set **Debug probes file** to the matching
   `fpga_debug.ltx`. Leave the probes field empty for a normal image that has no
   `.ltx` file.
4. Select **Program** and wait for Vivado to report success.
5. Refresh the device once. When using the debug image, open the Hardware window
   and confirm that the expected ILA cores are discovered.

The `.bit` file configures FPGA SRAM through JTAG. That configuration is lost
after power-off or another FPGA configuration event.

## PCIe enumeration after programming

PCIe Root Complex enumeration normally happens before an interactive JTAG
download finishes. After programming, use a supported PCIe bus rescan for a
quick retry, but use the following sequence for the reliable acceptance test:

1. Program the FPGA.
2. Keep the FPGA configured.
3. Cold-boot or reset the PCIe host so the endpoint is present during
   enumeration.
4. Confirm the endpoint identity, negotiated width/rate, BAR0, and capabilities.

Refreshing Device Manager alone does not guarantee a full PCIe link retrain or
Root Complex enumeration.

After PCIe enumeration, continue with [Board bring-up](board-bringup.md). The
RawUDP cable and packet tests use physical **SFP1 / RTL lane 0** only. **SFP2 /
lane 1** remains TX-idle and RX-drain.

## Persistent configuration boundary

The normal and debug Tcl flows call `write_bitstream -bin_file`, so they emit
both `.bit` and `.bin` files. The current repository does not define a
configuration-memory part or call `write_cfgmem`:

- `.bit` is the verified input for direct JTAG configuration.
- `.bin` is an accompanying bitstream output; its existence alone does not
  establish a complete board-flash procedure.
- `.mcs` is not currently generated and is not required for JTAG programming.

The XDC selects `SPIx4`, a four-bit SPI bus, and falling-edge bitstream
configuration. Before using **Add Configuration Memory Device**, confirm the
board's exact QSPI part, capacity, interface, and address mapping from board
documentation. Then generate the matching cfgmem image and verify power-cycle
boot as a separate acceptance gate.

## Record programming evidence

Record the source commit and image hashes before board testing:

```powershell
git rev-parse HEAD
Get-FileHash -Algorithm SHA256 .\.build\release\fpga.runs\impl_1\fpga.bit
Get-FileHash -Algorithm SHA256 .\.build\release\fpga.runs\impl_1\fpga.bin
Get-FileHash -Algorithm SHA256 .\fpga_debug.bit, .\fpga_debug.ltx
```

Hash only the image type that was actually programmed. For the debug flow,
retain the BIT/LTX pair, Vivado programming log, PCIe enumeration output, SFP1
packet capture, and ILA exports together. See [Validation status](validation.md)
for the distinction between simulation evidence and open hardware gates.
